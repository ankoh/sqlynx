# Rust rewrite of dashql-core

The C++20 core (`packages/dashql-core`) has been rewritten in Rust, and the C++ core is deleted. The Rust
core is a set of top-level packages; the app and `@ankoh/dashql-core` ship its wasm modules.

| Package | Crate | Content |
|---|---|---|
| `packages/dashql-parser` | `dashql_parser` | Scanner, keywords, names, parser (tables, actions, LR driver, completion probes), comment blocks |
| `packages/dashql-core` | `dashql_core` | Script, catalog, analyzer, cursor, completion, formatter, script diff, visualize, compiler, batch, planner, plan view model, sessions, shell |
| `packages/dashql-snapshots` | `dashql_snapshots` | Snapshot loading and encoders, YAML emitter, snapshotter |
| `packages/dashql-core-wasm` | `dashql_core_wasm_lib`, `dashql_core_wasm` (cdylib) | wasm-bindgen API shipped by `@ankoh/dashql-core` |
| `packages/dashql-shell-wasm` | `dashql_shell_wasm` | Shell wasm module (with the core bindings) shipped by the app |

## Decisions

- **Parser: bison tables, not LALRPOP.**
  - Bison stays the LALR(1) table compiler. `grammar/rust/tables.rs.m4` is a bison skeleton that
    emits the automaton and the Rust user actions of `grammar/rules/*.y`.
  - The LR driver is a hand-written port of the C++ `DriveLALR`.
  - Code completion drives the raw LR tables (state snapshots, LAC expected sets, suffix probes) and
    the grammar resolves its conflicts with a Postgres-style precedence ladder. LALRPOP supports
    neither.
- **Scanner: logos**, bug-compatible with the former flex scanner (`grammar/scanner.l`, deleted).
  - Every flex start condition is a `logos` lexer that matches bytes like flex.
  - The actions (`yyless`, `BEGIN`, nested comments, the lookahead filter) are hand-written around them.
- **JS boundary: wasm-bindgen with a new API.** FlatBuffers stays the payload format, so the generated
  TypeScript readers keep working.
- **Parse tree: unchanged by default.** Intentional changes follow [ast-changes.md](ast-changes.md).
- **Parity first, fixes later.** Known C++ bugs were reproduced and are listed in [quirks.md](quirks.md).
  With the C++ core gone, each one can be fixed as an ordinary change with a snapshot update.
- **Parity of semantics, not of incidental text.** Output that is an artifact of a C++ library (number
  formatting of rapidjson, c4 or `%g`) is not reproduced. The Rust core writes doubles with the shortest
  round-trip digits, and the snapshot tests compare numbers by value. For an infinite double the C++
  Vega-Lite generator wrote no value (invalid JSON); Rust writes `null`.
- **JSON is standard JSON.** Hyper plans and Vega-Lite specs are read and written with serde_json
  (`preserve_order`), numbers of the script are parsed with `str::parse::<f64>`. rapidjson's dialect
  (comments, NaN, trailing commas, NUL-terminated input, C strings, imprecise numbers, duplicate keys)
  and the glibc `strtod` and x86 cast behavior are not reproduced (see [quirks.md](quirks.md)).
- **Bazel only.**
  - Generated code comes from genrules, never `build.rs`.
  - Every crate package has its own `Cargo.toml`, and there is no Cargo workspace. The manifests only
    feed the isolated `@core_crates` crate universe (`MODULE.bazel`, lockfile
    `bazel/core_crates/Cargo.lock`).
  - Never `cargo build` or `cargo test`.

## Verification

1. **Snapshots.** The Rust tests read `snapshots/**/*.yaml` and compare structurally, including the
   key order of every map; numbers compare by value. The files are generated by the Rust snapshotter
   (see [Snapshotter](#snapshotter)).
2. **Unit tests**, ported from the C++ suites. `:dashql_buffers_test` pins the FlatBuffers enum
   ordinals the code relies on.
3. **dashql-core-js and app test suites** against the Rust wasm modules.

Until the C++ core was deleted, a **differential oracle** checked the port against it:
`oracle_ffi`, a C ABI over the C++ core linked natively into the Rust tests of the `dashql-oracle`
crate, answered in the snapshot serialization. The `*_differential_test` targets compared both cores
on snapshot inputs, every prefix and cursor position for completion, TPC-H/DS, random sentences
derived from the grammar, and fuzzed inputs. `:dashql_grammar_table_parity_test` checked that the C++
and Rust rule sets described the identical automaton. All of them were deleted with the C++ core; the
phase results below mention them as history.

## Phase 9: C++ core removed

The C++ core is deleted, with everything that only existed for it:
- `packages/dashql-core` (C++20) with its tests, tools and the C++ FlatBuffers codegen
- the differential oracle: the `dashql-oracle` crate, `oracle_ffi`, all `*_differential_test` targets,
  `oracle_parser_snapshot_test` and `dashql_grammar_table_parity_test`
- flex and `grammar/scanner.l`, the C++ (`lalr1.cc`) parser generation
- the C++ externals (rapidjson, rapidyaml/c4core, ankerl, Arrow C++, md4c, flex), `WORKSPACE` and the
  hedron `refresh_compile_commands`

The grammar has a single rule set again: `grammar/rules/*.y` contain the Rust actions directly and are
checked in. `grammar/rust/translate_actions.py` and the `--lang` flag of `assemble_grammar.py` are
gone. The crates moved from `packages/dashql-core-rs/<crate>` to the top-level packages above, and the
coverage workflow (`.github/workflows/coverage.yml`) covers the Rust core.

No golden tests replace the deleted differentials. In particular, script signatures
(`dashql_core::signature`) are not pinned: they need not stay stable across versions.

## Phase 0 results (2026-10-20)

**Bison skeleton**
- `tables.rs.m4` emits the full grammar as narrow integer tables, the same types as the C++ tables:
  - 639 terminals, 359 nonterminals, 1825 rules, 2791 states
  - `yylast` 69019
  - `i16` for `yytable`/`yycheck`, `i32` for `yypact`
- It also emits the symbol names and `S_*` symbol kinds.
- `:dashql_grammar_table_parity_test` checked every table entry, constant and symbol name against the
  lalr1.cc output (deleted with the C++ parser).
- The action path works: `:dashql_parser_skeleton_test` runs a calculator grammar with Rust block
  actions, typed `$n`, `@n`/`@$`, precedence, default actions and errors raised from actions.
- Why our own skeleton instead of the `rust-bison-skeleton` crate:
  - That crate's m4 files carry bison's GPL header, so we can't vendor them.
  - It brings its own parse loop, but we need the tables for a ported driver.
  - Our skeleton includes only `c-like.m4` from the bison installation at build time.
- Bison has to run outside the sandbox (`local = 1`).

**Oracle and harness**
- `:oracle_parser_snapshot_test` (deleted) replayed all 506 parser cases through the C++ oracle, and all
  passed.
- That covered 18 cases the C++ parser snapshot suite never registered (`error_recovery.yaml`,
  `functions.yaml`, `sql_function.yaml`, `tpch_schema.yaml`); `:parser_snapshot_test` runs all cases.

**Baselines** (WSL2, x86_64)

## Phase 1 results

**Scanner**
- `dashql_parser::scanner` generates its DFAs with `logos` (`=0.16.1`). The rules of every flex start
  condition are one `#[derive(Logos)]` enum (`Initial`, `Xc`, `XbXh`, `Xq`, `Xd`, `Xbt`). The enums
  match bytes (`utf8 = false`, byte-string patterns), so `\x80-\xFF` are identifier bytes like in flex.
- Flex semantics on logos:
  - **Start conditions:** the scanner keeps the flex state and runs the lexer of the current state for
    exactly one match. An action can then switch the state or put text back with `yyless`, and the
    next match starts a fresh lexer at the new position. The `<<EOF>>` rules are handled before
    matching.
  - **Longest match:** logos takes the longest match like flex.
  - **Rule order:** logos breaks ties by priority and rejects equal priorities at compile time, where
    flex takes the earlier rule. The default priority (2 per byte or class) already ranks `{comment}`,
    `{xcstart}` and the fixed tokens correctly. Explicit priorities put `{operator}` below the
    single-character tokens, `{other}` below everything, and `{quotefail}` below `{quotestop}`.
  - **Rules with the same action** are one variant with several patterns, such as `{xcinside}`,
    `{op_chars}` and `\*+` in `xc`.
  - **Trailing context:** `{raw_question_mark}/({ident_cont}|{dquote})` is a single `?` whose action
    checks the next byte.
  - **`%option caseless`:** the patterns spell out both cases (`[bB]'`, `[Ee]`). The Hyper obfuscation
    markers stay case-sensitive.
- Line breaks are recorded for the whole match before the action runs, so text put back with `yyless`
  is counted again, like the C++ `YY_USER_ACTION`.
- The lookahead filter is ported literally.
- Until 2026-10 the scanner was hand-written: it computed the longest match of every rule of the
  current start condition and gave ties to the earlier rule. The logos scanner replaced it with no
  difference in the differential test, also in a run with 2 million fuzz inputs. On TPC-DS q1 it is
  about 3% slower (`scan_text` 2.25 µs before, 2.33 µs after). `bench_pipeline_ctes` scans at the same
  speed (1.98 ms for 1000 CTEs before and after). The release `core_wasm` grew by 10.7 kB (2.2 kB
  gzipped).

**Differential test**
- `:scanner_differential_test` compares the complete scanner output against the C++ scanner on:
  - every snapshot input of every category, and their prefixes
  - 32,000 deterministic fuzz inputs
- The compared output covers symbols and values, errors, line breaks, comments, obfuscated literals,
  names, comment blocks, and comment warnings.
- There are no differences.
- New quirks found along the way are in [quirks.md](quirks.md).

**Comment blocks**
- `dashql_parser::comment_blocks` ports `GroupComments`.
- Metadata JSON is validated with serde_json instead of rapidjson.

## Phase 2 results

**Rust rule set**
- Until phase 9, `//grammar:rust_rule_files` translated the C++ actions of `grammar/rules/*.y` into
  Rust in the build, using `grammar/rust/translate_actions.py`. All 1238 actions translated, and the
  rules themselves were copied verbatim. `assemble_grammar.py --lang rust` derived the Rust prologue
  (tokens, types) from the C++ one.
- `:dashql_grammar_table_parity_test` asserted that both rule sets describe the identical automaton.
  Only `yyrline` (debug line numbers) differed.
- With the C++ core removed, the translated rules were checked in as `grammar/rules/*.y`, and the
  translator and `--lang` were deleted.

**Runtime** (`dashql_parser::parser`)
- `ParseContext` is ported with interior mutability, so translated actions nest calls in the same
  order as the C++ actions. Semantic values are `Copy`, with lists and n-ary expressions in arenas.
- The driver ports the lalr1.cc loop:
  - full LAC
  - verbose errors and the SCONST hint
  - `error` token recovery, `YYERROR` and `yyclearin`
  - the custom `YYLLOC_DEFAULT`
- `feed` and `lac_check` are exposed for the completion probes.

**Gates**
- `:parser_snapshot_test`: all 506 parser snapshots pass, produced by the Rust parser and a port of
  the C++ encoder.
- `:parser_differential_test`: raw output equals the C++ parser. The comparison covers every node
  field, statements, errors with hints, vis spec spans, feature flags, names, and obfuscated
  literals. The inputs are:
  - all snapshot inputs and their prefixes
  - 3200 random sentences of the grammar (random walks through the LR automaton over acceptable
    tokens, about 85 tokens each)
  - 8000 fuzz inputs

**Performance** (`bazel run -c opt //packages/dashql-core:bench_pipeline`, TPC-DS q1, same
machine as the baseline):

| Measure | Rust | C++ |
|---|---|---|
| scan | 2.3 µs | 3.2 µs |
| parse | 8.6 µs | 7.7 µs |

Changes that got the Rust code here:
- **Scanner:** keyword lookup through a generated FNV hash table, an open-addressing name registry,
  and no per-identifier allocations.
- **Parser:**
  - each grammar action is its own function, so `reduce` has a small frame
  - list allocations are recycled
  - the parse context state uses a `RefCell` only in debug builds

## Phase 3 results

- `script_diff` is ported (`dashql_core::script_diff`). `:diff_snapshot_test` passes the 13 diff
  snapshots and a differential against `tools/oracle_ffi_script_diff.cc` over edited snapshot inputs.
- The formatter is ported (`dashql_core::formatter`).
  - `:formatter_snapshot_test` passes all 422 cases (1287 expectations), including the reparse checks
    of the `coverage_` cases.
  - `:formatter_differential_test` compares text and unformattable nodes against
    `tools/oracle_ffi_formatter.cc`: 238k whole-script and 12.5k single-node comparisons, covering
    every snapshot input under 16 configs (modes, dialects, keyword cases, widths, indentation, debug
    mode), prefixes, and fuzz inputs with comments. 0 differences.
- `:formatter_validation_hyper_test` executes the Rust formatter output of the 91 cases with a `hyper`
  validation in Hyper: a fresh database per case, the setup script, then every expectation statement by
  statement. Hyper only ships a C++ SDK, so the test links `//packages/hyper-api:hyper_ffi`, a C ABI
  over it that never throws. It passes the same 91 cases as the C++ suite it replaces
  (`formatter_validation_hyper_tests`, deleted), and it picks up every snapshot file with a validation
  instead of a hand-maintained list.
- Open: the idempotency check.
- The Hyper plan view model is ported (`dashql_core::view`) and reads plans with serde_json.
  `:plan_view_model_snapshot_test` passes 36 of 36 plans (including the `pipelines` section, which the
  C++ suite skips), the 19 `hyper_plan_test.cc` tests pass, and `:plan_view_model_differential_test`
  finds 0 differences in about 20,000 comparisons of standard JSON plans (bit-identical layout) against
  `tools/oracle_ffi_view.cc`.

**Attribute lookups.** The C++ core looks up object attributes through compile-time
`frozen::unordered_map`s. `dashql_parser::attrs!` fixes the keys at compile time too (duplicate
keys fail constant evaluation) and scans the children against the constant key array, which LLVM
vectorizes. Measured with `bench_pipeline` (`attrs_21/*`, the 21 keys of a vis scale):

| Children | Constant-key scan | Static perfect hash | Direct-index table |
|---|---|---|---|
| 5 | 4 ns | 8 ns | 9 ns |
| 21 | 11 ns | 13 ns | 24 ns |
| 40 | 14 ns | 18 ns | 28 ns |

Formatting TPC-DS q1 (`format_query`, added to both benchmarks) takes 6.1 µs in Rust and 11.4 µs in
C++. The hash table variant was 6.5 µs, so it was dropped.

## Phase 4 results

- The catalog (`dashql_core::catalog`) publishes analyzed scripts and descriptor pools as immutable
  entries shared through `Arc`. An analyzed script holds the entries it was analyzed against, which
  replaces the `retained_catalog_dependencies` lease. Id reservations go through the catalog by
  shared reference, so an analysis only needs `&Catalog`.
- The analyzer (`dashql_core::analyzer`) ports the four passes with the 1024-node morsel
  interleaving of the `PassManager`, so expression ids match. Objects live in vectors of the
  analyzed script and reference each other by index.
- `:analyzer_snapshot_test` passes all 101 analyzer snapshots on the keys the C++ suite compares.
- `:analyzer_differential_test` compares the complete encoding, including visualizations, against
  `tools/oracle_ffi_analyzer.cc` with 0 differences. Inputs: every analyzer case with prefixes, every
  snapshot input of every category alone and against the snapshot catalogs with prefixes, and 3200
  fuzzed scripts against fuzzed catalogs.
- `dashql_core::signature::compute_signature` equals `Script::ComputeSignature` on every snapshot
  input, their prefixes and 4000 fuzz inputs (`:signature_differential_test`).
- Open: the FlatBuffer packing of the analyzed script, and the catalog,
  descriptor and analyzer unit tests.

**Performance** (TPC-DS q1 against the TPC-DS schema in the catalog, `bench_pipeline` and
`benchmark_pipeline`):

| Measure | Rust | C++ |
|---|---|---|
| analyze (analysis only) | 10.6 µs | 12.7 µs (`analyze_query_only`) |
| `Script::Analyze` (rescan, reparse, analyze) | | 29.0 µs (`analyze_query`) |

`analyze_query` of the C++ benchmark rescans and reparses on every iteration, because a script whose
names carry analyzer tags is never reanalyzed in place. `analyze_query_only` measures the analysis
alone. What made the Rust analyzer fast, from 25.6 µs:
- node states move up the tree by taking over the child buffers instead of copying (C++ splices
  intrusive lists),
- visualization node states exist only for nodes with visualization state,
- the property graph ancestor walk is skipped for scripts without graph syntax,
- the maps use FxHash (`dashql_core::hash`) instead of SipHash.

Name resolution could also store its node states as linked lists like C++, which would remove the
remaining per-list allocations.

## Phase 5 results

- The LR probes of the completion (`DriveLALR` and its policies) are ported to
  `dashql_parser::parser::probe`: `parse_until_with_snapshot`, `parse_until_after`, and the suffix
  probes over a state snapshot, with the 128-reductions bound.
- `dashql_core::cursor` ports `ScriptCursor` and the location lookups, `dashql_core::completion`
  ports the completion. Name lookups use per-entry suffix indexes in the case-insensitive order of
  the C++ `btree::multimap`. Candidates are ranked by score, then by name (case-insensitive, then
  byte order), keywords before names that spell the same. C++ leaves such ties to the unstable
  `std::sort`, so the differential tests compared them in a canonical order.
- `:completion_snapshot_test` passes all 161 completion snapshots (including the analysis of the
  catalog and editor scripts).
- `:completion_differential_test` compares the complete encoding with
  `tools/oracle_ffi_completion.cc` at every cursor position of every completion snapshot, at sampled
  positions in all other snapshot inputs (with and without a catalog), and at the end of prefixes:
  0 differences.
- Open: `completion_test.cc` (33 tests) and `cursor_test.cc`, which need the `Script` facade.

## Phase 6 progress

- **Script facade** (`dashql_core::script`): the text is a ropey rope indexed by code points like the
  C++ rope, so edits in the middle of large scripts stay logarithmic. A script does not reference its
  catalog; analysis takes `&Catalog`, and dropping a script leaves the catalog alone.
- **Packing** (`dashql_core::pack`): scanned, parsed and analyzed scripts, cursors and completions.
  `:pack_differential_test` and `:completion_differential_test` unpack the FlatBuffers of both cores
  into the object API and compare them, including the generated visualization specs.
- **Visualize** (`dashql_core::visualize`): the Vega-Lite generator and parser, Markdown and UMAP.
  `:visualize_snapshot_test` passes 27/27, `:visualize_differential_test` finds 0 differences over 38k
  analyzed scripts and 31k Vega-Lite texts (standard JSON).
- **Markdown**: templates are parsed with pulldown-cmark (CommonMark, no extensions) instead of a port of
  md4c, so the documents differ from C++ in details:
  - adjacent text is one text node (md4c cuts text at every mark, entity and line break),
  - list tightness is derived from the item paragraphs (pulldown-cmark does not report it),
  - the last line of a code block keeps no line break that is not in the template, and trailing
    whitespace at the end of the template is dropped,
  - the md4c deviations from the spec in [quirks.md](quirks.md) are gone (tabs in code blocks are kept,
    a closing fence must be indented like its list item, NUL characters become U+FFFD exactly once, ...).

  `:visualize_differential_test` compares the documents by meaning (adjacent text merged, trailing
  whitespace and tightness ignored) on the snapshot scripts, handcrafted corner cases and 8k well-formed
  generated templates. 128k fuzzed templates hit corner cases where md4c deviates from CommonMark, so
  they only have to compile in both cores to the same fields. pulldown-cmark makes the release core
  module 85 KB larger (26 KB brotli) than the md4c port.
- **Compiler** (`dashql_core::compiler`): `:compiler_differential_test` compares the packed
  `ScriptCompilationResult` with C++ on all snapshot inputs and prefixes.
- **Planner** (`dashql_core::planner`): `:planner_snapshot_test` passes all 38 planner snapshots.
- **Batch** (`dashql_core::batch`): `:batch_differential_test` compares `BatchResult`s with the
  nested FlatBuffers unpacked. A request with invalid UTF-8 script text fails as a whole in Rust (the
  FlatBuffers verifier rejects it), C++ reports it per script.
- **Unit tests**: 105 tests ported from `completion_test`, `cursor_test`, `catalog_test`,
  `unification_test`, `name_tagging_test`, `analyzer_{declaration,delete,insert}_test`,
  `script_test`, `topk_test` and `string_conversion_test` (`DASHQL_CORE_UNIT_TESTS`). Left out:
  writes of the C++ public `text_version`, invalid UTF-8 edits (Rust takes `&str`), and
  `CATALOG_SCRIPT_NOT_ANALYZED` (only analyzed scripts can be loaded). Catalogs carry a unique id
  that analyzed scripts record, so loading a script of another catalog fails with
  `CATALOG_MISMATCH` as in C++.

## Phase 7 results

- **ScriptSession** (`dashql_core::script_session`): sessions share their catalog through a
  `CatalogHandle` (`Rc<RefCell<Catalog>>`) and borrow it only during a call; dropping a session drops
  its script from the catalog like the C++ destructor. Editor events, cursors, analysis, completion,
  compilation, formatting, dashboard rewrites, diffs and catalog publication are ported, including
  the UTF-8 and UTF-16 offset projections (`utils::rope`).
- **ScriptExecution** (`dashql_core::script_execution`): the C++ coroutine is an explicit state
  machine (phase, statement index, pending statement id).
- **Script**: statement text, dashboard rewrites, formatting, unformattable nodes and statistics.
- **Tests**: `:script_session_test` (34: all 29 of `script_session_test.cc`, 3 of `api_test.cc`, 2
  new) and `:script_execution_test` (6). `:session_differential_test` runs 88 random episodes over
  both offset units against a stateful C++ oracle (`tools/oracle_ffi_session.cc`): about 231k
  comparisons of updates, texts, versions, revisions and the catalog version, 0 differences.
- **Planner**: takes the catalog of each script (`PlannerInput`) and reports scripts of different
  catalogs like C++.

**Deviations**
- An editor event with invalid UTF-8 inserts fails buffer verification with `INVALID_EVENT`; C++
  reports `INVALID_UTF8`. Rust strings are always valid UTF-8.
- Memory statistics: rope, scanner input, AST bytes and the name index size match C++. Symbol,
  name dictionary, analyzer description and name index bytes measure the Rust data structures.
- Timings stay 0 on wasm32, because `Instant` panics there.

**Notes**
- `ANALYSIS_FAILED` was never covered by the session differential: the only known input that fails
  analysis (a qualified function name) hit an `assert` in the C++ fastbuild oracle.
- `ScriptCompiler::Compile` (C++) kept a reference to the parsed script while the `Analyze(false)`
  it called could replace it. Never hit, but undefined behavior.

## Phase 8–10 results

The app and `@ankoh/dashql-core` run on the Rust core. Until its removal in phase 9, the C++ core only
built natively and served as the oracle of the differential tests.

- **wasm-bindgen API** (`dashql-core-wasm`, an rlib `:dashql_core_wasm_lib` wrapped by the cdylib
  `:dashql_core_wasm`): `Catalog`, `Script`, `ScriptBatch`, `ScriptSession`, `ScriptExecution`,
  `SessionList`, `PlanViewModel`, `plan`, `processBatch`, `parseVegaLiteToVisualize`. Results are
  FlatBuffer bytes owned by JS, errors are exceptions. Scripts and sessions share their catalog
  (`Rc<RefCell<Catalog>>`); freeing them drops them from the catalog like the C++ destructors.
  wasm-bindgen 0.2.105 cannot take `Option<&T>`, so formatting into another catalog is `formatInto`.
- **`dashql-core-js/src/api.ts`** keeps its public classes. `ptr` now wraps a wasm-bindgen object
  (`assertNotNull()` returns it) and `FlatBufferPtr` owns a `Uint8Array`, so results need no freeing.
  `DashQL.create({ wasmBinary | module })` replaces Emscripten's `instantiateWasm`. A wasm-bindgen
  module is instantiated once per page, so all `DashQL` instances share one wasm memory; each still
  owns and frees its own objects. `print`/`printErr` are accepted but unused.
- **Shell** (`dashql_core::shell`, arrow-rs 60): prompt buffer, VT100 terminal, Arrow renderer,
  session relations and the effect protocol (the coroutines are a list of pending effects). The
  shell module `:shell_wasm` re-exports the core bindings, so the app creates its `DashQL` on it.
  `packages/dashql-app/src/shell/api.ts` uses the `Shell` class instead of the C ABI.
- **Shell cells are formatted by arrow-cast** (`ArrayFormatter`), not like Arrow C++
  `Scalar::ToString`: floats with ryu, temporal values in ISO 8601, binaries in hex, nested values as
  `[1, null, 3]` or `{x: 1, y: a}`, a dictionary cell as its value. Named time zones are shown in UTC
  (chrono-tz is not linked), columns that arrow-cast cannot format show their type. See
  [quirks.md](quirks.md#shell-packagesdashql-coresrcshell).
- **Tests**: `dashql-core-js` vitest (255), Node smoke and tarball consumer tests, browser tests in
  Chromium and Firefox, and the app tests (185 files, 9620 tests) in Chromium and Firefox pass.
  The shell tests (51 + 22 + 10) are ported; `:shell_differential_test` compares 24k Arrow renders and
  1600 random sessions with 0 differences. Renders are compared byte for byte for tables of null,
  boolean, integer and string columns, which both shells print alike; tables of all other types are
  compared by status, like Arrow errors.
- **Shell text measurement** uses `unicode-segmentation` (extended grapheme clusters) and `unicode-width`
  (terminal columns) instead of a port of utf8proc 2.4 (Unicode 12.1). Flags are 2 columns wide, emoji
  presentation sequences 2, the soft hyphen 0, and newer code points have their current properties. The
  differential test only generates texts that both measure alike.

## Snapshotter

`//packages/dashql-snapshots:snapshotter` replaces the C++ snapshotter (`tools/snapshotter.cc`, deleted).
`bazel run //snapshots/<category>:update` runs it, `bazel run //snapshots:update` updates all categories.
It takes the same flags: `--source_dir=<repository> [--filter=<category>]`.

- The encoders in `dashql_snapshots::encode` build styled trees (`dashql_snapshots::ryml::Node`): every
  scalar carries the style the C++ encoder gave rapidyaml (plain unless the emitter must quote it,
  double-quoted, single-quoted, block literal), every container block or flow style, and maps keep
  their key order. The snapshot tests compare the same trees structurally (`Node::to_yaml`).
- `ryml::emit` ports the rapidyaml 0.12.1 emitter, including its quirks: flow sequences without spaces
  (`[0,2]`), the scalar style choice of unstyled values, `|2` for block literals with leading spaces.
  `inject_blank_lines` ports `InjectBlankLinesInSnapshot`.
- `ryml::parse` reads templates with the styles rapidyaml records (scalar styles, flow and multi-line
  flow containers) through the event parser of yaml-rust2. Analyzer, completion, planner and visualize
  write their templates back with the results appended, so the template styles must survive.
- Gate: deleting all generated files and regenerating them gives byte-identical files in all
  categories. A differential run against the C++ snapshotter over extra templates (odd quoting,
  flow and multi-line flow containers, quoted keys, nulls, folded scalars, other top-level keys) found
  no differences.
- Deviation: when a location hint (`prefix..suffix`) cuts a multi-byte UTF-8 character, C++ wrote the
  invalid bytes, Rust writes U+FFFD. No snapshot is affected, and the Rust tests cannot load files with
  invalid UTF-8.
- Doubles in the analyzer and UMAP encodings are written with Rust's `{:?}` formatting (`-45.0`,
  `1e-5`), where C++ wrote `%g`-style `-45` and `1e-05`.
